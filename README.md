# VCU Hospital Bed Turnover Simulation (Data Forge 2026)

Patients wait for beds that are physically empty but not yet cleaned. We call
these **ghost rooms**. This project simulates a 905-bed hospital (modeled on VCU
Medical Center, built from Virginia state-level data) to measure how much bed
wait comes from slow cleaning handoffs, and tests whether alerting cleaning
staff the moment a nurse marks a patient ready to leave reduces it.

**Stakeholders:** charge nurses (who check patients in and out), Environmental
Services (EVS) cleaning staff, and the patients waiting for a bed.

### The story

- **Today (baseline):** A nurse discharges a patient, but EVS is not told.
  Each cleaner stays in an assigned hall of 10 rooms and checks it about once
  an hour while on duty, even if the round finishes early. During staffed
  hours, a room normally waits up to one round to be noticed; after hours it
  waits until a cleaner returns. The pilot models only one day-shift cleaner
  repeated over the week, so overnight waits are not representative of a full
  EVS roster.
- **Change (intervention):** When the nurse marks the patient ready to leave,
  EVS gets an alert. When the patient leaves, the room goes straight into a
  cleaning queue: rooms with an emergency patient waiting first, then
  elective, then oldest discharge.

### Bed states and who triggers them

`available → occupied → discharge_pending → needs_cleaning → cleaning → available`

| Transition | Triggered by | Baseline | Intervention |
|---|---|---|---|
| `available → occupied` | Nurse: **check-in** | Same | Same |
| `occupied → discharge_pending` | Nurse: **current care** = ready | EVS not told | EVS alerted |
| `discharge_pending → needs_cleaning` | Nurse: **check-out** | Waits for a cleaner's round | Queued for next free cleaner |
| `needs_cleaning → cleaning` | Cleaner starts | | |
| `cleaning → available` | Cleaner finishes | | |

Emergency patients get queue priority for beds, but an occupied bed is never
taken from a patient mid-stay.

---

## What We Measure

1. **Ghost-room time:** minutes a room spends in `needs_cleaning`.
2. **Idle bed-hours per day:** beds empty but not usable.
3. **Wait for an inpatient bed**, reported separately for emergency and elective patients.
4. **Cleaner utilization**, so faster turnover does not quietly overload EVS staff.

**What we do not claim:** ED boarding time (there is no ED data), financial
value, or results for any real hospital. Bed wait is the stand-in for ED
boarding, and results should say so.

### Step 2: Baseline simulation (in progress)

- **Build:** `src/week_sim.py` (bed state changes, shared with Step 3) and
  `src/sim.py` (the SimPy simulation). Bed transitions are kept independent of
  SimPy so the API can reuse them without depending on the simulation engine.
- **Pilot scope:** a 10-room synthetic hospital-mix hall, one cleaner, starting
  on 2017-01-02 and running for seven consecutive days through 2017-01-08.
  The date can be changed after the first run. On the starting date,
  occupancy is 659/905, so 7 of 10 rooms start occupied; occupancy says whether
  a room is usable, not whether it is dirty. The remaining rooms get a seeded
  50% dirty-state draw; rooms emptied by a simulated patient discharge need a
  discharge clean. Hospital-wide appointments are thinned by 10/905 to scale
  arrivals to the hall.
- **Generated pilot inputs:** run `python -m src.pilot_data` to create
  [data/pilot_initial_rooms_2017-01-02.csv](data/pilot_initial_rooms_2017-01-02.csv)
  and [data/pilot_arrivals_2017-01-02.csv](data/pilot_arrivals_2017-01-02.csv)
  from the assumptions and source datasets. The room file is the starting
  census; the arrivals file covers the full seven-day horizon. Regenerate after
  changing the date, assumptions, seeds, or source files.
- **Patient stays:** generate right-skewed (log-normal) lengths using each
  arrival category's daily mean LOS. Since individual LOS variability is not
  observed, use a provisional CV of 0.50 and compare 0.30 and 1.00. ICU uses
  the overall average LOS; a missing category mean must not be silently
  replaced.
- **Inputs:** hospital layout and EVS crews from
  [data/assumptions.yaml](data/assumptions.yaml); stays and cleaning times
  that are usually near average but sometimes run much longer (see
  [Modeling rules](#rules-everyone-follows)); arrivals that are busier in the
  morning; a limited number of cleaners on 60-minute rounds.
- **ER flow (team direction; not implemented in the current pilot):** patients
  arriving through the ER receive an ER bed, stay 1–6 hours (median 2.5 hours),
  and then either transfer to a ward (15%) or leave the hospital (85%).
  Scheduled procedures/admissions go directly to wards and do not occupy ER
  beds. The current pilot remains ward-only; see
  [data/assumptions.yaml](data/assumptions.yaml) for the modeled boundary and
  unresolved inputs.
- **Pilot run:** `python -m src.sim` runs a 168-hour window with one day-shift
  cleaner each day (7 AM–3 PM), modeled as six consecutive productive hours
  beginning at 7 AM. Arrivals and category LOS means are drawn from each
  simulated date. A clean already started can finish after productive hours
  and may extend beyond that shift. The schedule and zero discharge-processing
  delay are assumptions; this single-hall run validates the pipeline, not
  hospital-wide performance. The runner returns the event log, cleaner
  activity, metrics, and a per-room/per-day table of state-hours and turnover
  counts in memory; results storage remains an open team decision. The CLI
  prints this daily room table after the overall metrics. The current run's
  shareable table is [data/pilot_daily_room_summary_2017-01-02.csv](data/pilot_daily_room_summary_2017-01-02.csv).
- **Draft validation plan — for team review, not yet accepted:**
  1. Confirm input coverage and scaling: all seven simulated dates have daily
     census and synthetic appointments; starting census maps to 7/10 occupied
     rooms; sampled arrivals stay within the horizon; and the sampled arrival
     count is compared with its thinning expectation (`appointments × 10/905`).
  2. Verify mechanics: repeated runs with the configured seeds are identical;
     every state change follows the allowed bed cycle; capacity is never
     exceeded; and the cleaner works in the assigned hall during daily
     productive hours, except to finish an active clean. If the sampled week
     does not exercise a queue, use a controlled test case to verify emergency
     and elective priority rather than interpreting zero wait as validation.
  3. Reconcile time accounting: the seven-day denominator is 42 productive
     cleaner-hours; ghost time is part of idle-bed time; completed work,
     overtime, unfinished cleaning, and patients queued at the horizon are
     reported distinctly.
  4. Compare daily occupancy and arrival patterns with source aggregates as
     plausibility checks, not patient-level validation. Do not compare this
     one-cleaner/10-room utilization directly with whole-floor or hospital
     utilization.
  5. Review sensitivity with the same seed, changing one assumption at a
     time: LOS CV (0.30/0.50/1.00), unnecessary-check time (1/2/5 minutes),
     round interval (30/60/120 minutes), and initial dirty probability
     (candidate values 25%/50%/75%, for team review).
     Report that fixed-seed sensitivity is not a replication-based uncertainty
     interval.
  6. Before calling the baseline validated, agree on acceptable tolerances
     for aggregate comparisons and whether multiple start dates or independent
     seeds are required. One week and one seed cannot establish stable
     estimates or hospital-wide effects.
- **Show the problem:** "before" visuals of ghost-room time by hour of day,
  idle bed-hours, cleaner workload by hour, and patient wait for a bed.
- **Done when:** the team approves the aggregate-comparison tolerances;
  reproducibility, state and time-accounting invariants pass; daily trends are
  compared with [data/vcu_master_daily.csv](data/vcu_master_daily.csv) with
  proxy limitations stated; and sensitivity results are documented. The
  10-room/one-cleaner utilization is not treated as a direct match to
  whole-floor ward or ICU utilization.
- **Open questions:** the pilot is a hospital-mix proxy, not a specific ICU or
  ward floor; whether that is suitable can be revisited after the first run.
  Also unresolved: how long before departure the discharge order is written,
  when occupied-room cleans happen, and how to model the shared night cleaner
  in later full-floor runs. Use 2 minutes as a provisional wasted-check
  estimate and test 1/2/5 minutes because no local time study exists.
  Patient-level LOS variability is assumed and sensitivity-tested; synthetic
  care categories are not clinical diagnoses.

### Step 3: Intervention (planned)

- **Shared functions** in `src/week_sim.py`: `check_in()`, `current_care()`,
  `check_out()`. Both the simulation and the API call these so they cannot
  drift apart.
- **API demo** (`src/api/`, FastAPI), pingable from a terminal. The workflow
  routes return hello-world acknowledgments while recording patient bed state
  in a local JSON file:

  | Endpoint | Effect |
  |---|---|
  | `POST /check-in` | Record the synthetic patient ID as occupying a bed |
  | `PUT /current-care` | "Needs more time" keeps the stay; "ready" moves to `discharge_pending` |
  | `POST /check-out` | Room enters the cleaning queue |
  | `GET /patients/{patient_id}/status` | Read the patient's current bed state |

  Run locally with `uv run uvicorn src.api.main:app --reload`.

  In PowerShell, exercise the workflow with `curl.exe` (use a new patient ID
  when repeating the sequence):

  ```powershell
  curl.exe -X POST http://127.0.0.1:8000/check-in -H "Content-Type: application/json" -d '{"patient_id":"demo-001"}'
  curl.exe -X PUT http://127.0.0.1:8000/current-care -H "Content-Type: application/json" -d '{"patient_id":"demo-001","update":"ready"}'
  curl.exe -X POST http://127.0.0.1:8000/check-out -H "Content-Type: application/json" -d '{"patient_id":"demo-001"}'
  curl.exe http://127.0.0.1:8000/patients/demo-001/status
  ```

  Use `"needs_more_time"` instead of `"ready"` to keep the patient
  `occupied`.

- **Constraints:** single-process local JSON state at
  `data/api_state.json` (not a production multi-worker store), synthetic IDs
  only, no Epic/HL7/FHIR. In a real deployment this would read existing admit
  and discharge events from the EHR rather than add clicks for nurses.
- **Alert delivery is not implemented in this skeleton:** `PUT /current-care`
  records `discharge_pending` but does not yet notify EVS.
- **In the simulation**, the stay lengths already include patients who
  need more time; `current_care()` only sets when the discharge order happens.
- **Done when:** a terminal sequence moves one bed through every state and
  emits the EVS alert, and `src/sim.py` uses the same functions.

### Hackathon shortcut: turnover estimate (replaces the state machine)

Because of time, the full event-driven state machine is cut. Instead,
`src/turnover_estimate.py` estimates one room's wait under 60-minute rounds
versus an alert at `discharge_pending` (run `uv run python -m src.turnover_estimate`).
Plain language: the cleaner is alerted when the nurse marks the patient ready,
but can only start once the patient leaves; the saving is whatever dirty-room
waiting that overlap removes.

- **Inputs** (all in `turnover_estimate` in `data/assumptions.yaml`): patient
  leaves 30 min after "ready" on average, a free cleaner arrives in 5 min,
  alerts always work, rounds continue, and a busy cleaner delays the start by
  up to one clean. Busy chance is taken from each shift's cleaner utilization.
- **Outputs:** minutes saved per turnover and bed-hours recovered per day,
  by shift (day / evening / night) and overall.
- **Current result:** about 26 min saved per turnover and about 55 bed-hours
  per day recovered (day 27 min, evening and night 25 min).
- **Limits:** every key input is an assumption, and the shift splits are
  guesses. The perfect-alert assumption and a busy-cleaner model that ignores
  queues likely overstate the evening and night saving, when 0.5-1 cleaners per
  floor are on duty. Treat results as "if these hold", not observed.

### Step 4: Compare (planned)

- Run baseline and intervention with the **same seeds** and multiple
  replications so differences come from the change, not chance.
- **Sensitivity:** round interval 30 / 60 / 120 minutes, and evening crew size.
  The ghost-room saving depends on the assumed round interval, so show a range
  rather than one number.
- **Check the 3 PM crunch:** the day shift ends during the 2–5 PM discharge
  peak; one evening cleaner per floor may be the real bottleneck.
- **Deliver visualizations** that a charge nurse or EVS supervisor can read
  without explanation, likely as a dashboard:
  - Before vs after for each of the four metrics.
  - Ghost-room time and cleaner workload by hour of day (where the delay is).
  - A bed timeline (one row per bed, colored by state) for a sample day.
- **Done when:** the before/after visuals and a summary table of the four
  metrics, with ranges across replications and round intervals.

## Known Gaps (Who the Model Leaves Out)

- **The ED flow is specified but not implemented.** No ED visit counts or
  arrival timestamps are available. The proposed visit count is inferred from
  reconstructed via-ED ward admissions and the user-specified 15% admission
  share; it is not an observed ED census. The proposed model gives every ED
  arrival an immediate bed, so it does not estimate waits for an ED bed or
  boarding. The ED stay-distribution spread, actual room capacity, and EVS
  coverage remain unresolved. OR is not modeled.
- **Daily data is reconstructed** from monthly totals; day-to-day swings
  (about ±3%) are simulated, not observed.
- **Cleaning times are unverified** estimates; L&D and pediatric reuse
  med-surg times.
- **ICU is sized for the COVID-era peak**; in 2024 it averaged about 60% full.
- **Delivery nurse staffing is overstated** (postpartum days use the
  active-labor ratio).
- **COVID-19 data is missing** for Oct–Dec 2024; suppressed influenza values
  use calendar-month medians.

## Ideas Parking Lot

Good ideas that are out of the current scope. Pick one up once Step 4 has a
baseline to compare against.

- **Shortest-path cleaner routing:** needs a floor plan; travel time is likely
  small next to a 30-minute wait and 45-minute clean.
- **Elective scheduling optimization:** place elective admissions using a
  longer-than-typical planned stay (the length 75–80% of patients finish
  within) so they avoid the afternoon discharge crunch.
- **ED extension:** use the documented flow assumptions; review visit timing,
  stay-distribution spread, whether the 80-room reference is a capacity limit,
  and ED EVS coverage before implementation.
- **Earlier discharge times** (for example, discharge-before-noon) as a
  separate scenario.
- **EHR integration:** read real admit/discharge events instead of the demo API.

### Rules everyone follows

- **Tools:** use what is already in [Technical Stack](#technical-stack).
  To add a tool, propose it in a pull request that updates
  [pyproject.toml](pyproject.toml), `uv.lock`, and the stack table.
- **Assumptions:** any value not in the source data goes in
  [data/assumptions.yaml](data/assumptions.yaml) with an `# ASSUMPTION:`
  comment, and the same comment in code that uses it. Never hardcode it.
- **Repeatable randomness:** every function that uses random numbers takes a
  `seed`, so the same seed always gives the same result.
- **Stay lengths, waits, and cleaning times are lopsided.** Most patients stay
  close to the typical length, but a few stay much longer, and those long
  stays tie up beds. Never use a symmetric bell curve, which hides the long
  stays and can produce negative times. Use a right-skewed (log-normal) curve.
  For implementers, from average `m` and relative spread `c`:
  `sigma2 = ln(1 + c^2)`, `mu = ln(m) - sigma2/2`.
- **Arrivals vary by hour of day** (busier in the morning) and are random
  within each hour, not evenly spaced.
- **Code location:** reusable logic in `src/` (type hints and docstrings);
  notebooks import from `src/` and are for exploration and validation.
- **Out of scope unless agreed:** real EHR/HL7/FHIR, multi-hospital models,
  Postgres or other live databases, LLM features, staff scheduling optimization.

Project rules for Copilot are in
[.github/copilot-instructions.md](.github/copilot-instructions.md).

### 1. Build and Run via Container

From the repository root, start the local API server:

```powershell
uv run uvicorn src.api.main:app --reload
```

Keep this terminal open while using the API. Open
http://127.0.0.1:8000/docs to try the endpoints interactively; press `Ctrl+C`
in the terminal to stop the server.

### 2. Updating Dependencies and the Container

The image installs packages from `uv.lock` at build time (`uv sync --frozen`),
so **any dependency change requires a rebuild**, and the build fails if
`uv.lock` is out of date.

```bash
uv add <package>                      # add; updates pyproject.toml and uv.lock
uv remove <package>                   # remove
uv lock --upgrade-package <package>   # upgrade one package
uv lock                               # regenerate uv.lock after editing pyproject.toml by hand
```

Then:

1. Commit both [pyproject.toml](pyproject.toml) and `uv.lock`.
2. Rebuild: `docker build -t data-forge-2026 .`, or in VS Code
   **Dev Containers: Rebuild Container**.
3. Tell the team so they rebuild too.

The same rebuild applies after any change to the [Dockerfile](Dockerfile) or
[.devcontainer/devcontainer.json](.devcontainer/devcontainer.json).

### 3. Using Git from the Container

Git and the GitHub CLI are installed in the image, so nothing is needed on
your laptop. The repository history lives in your project folder, so commits
are kept on your laptop.

One-time setup, in a terminal inside the container:

```bash
gh auth login                                   # GitHub.com → HTTPS → log in with a web browser
```

In the Dev Container, your sign-in and git name/email are saved in a Docker
volume (`data-forge-2026-config`), so they survive rebuilds. With plain
`docker run`, add `-v data-forge-2026-config:/root/.config` to keep them.
To sign out: `gh auth logout`.

### 4. Using Mary (AI Copilot Agent)

This repository includes a dedicated custom Copilot agent, **Mary**, configured in [.github/agents/mary.agent.md](.github/agents/mary.agent.md). Mary is named in honor of Mary Eliza Mahoney, the first African American licensed professional nurse in the United States.

Mary enforces:
- Strict distinction between observed healthcare data and synthetic assumptions.
- Safe nurse-to-patient staffing ratio verification.
- Reproducible stochastic modeling using explicit random seeds.
- Transparent logging of all simulation assumptions in [data/assumptions.yaml](data/assumptions.yaml).
F
